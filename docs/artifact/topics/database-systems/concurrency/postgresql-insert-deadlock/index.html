두 트랜잭션은 왜 멈출까?

B가 20을 넣고 A가 21을 넣은 뒤, 서로 상대가 넣은 값을 추가하려고 합니다. 단계 버튼이나 자동 재생으로 어디서 멈추는지 확인해 보세요.

← 전체 학습 목차
학습 모형 · PostgreSQL 18 — 그림 속 100과 200은 트랜잭션을 구분하는 예시 번호입니다. 실제 번호는 달라질 수 있습니다.

실험 준비

id는 중복될 수 없는 기본 키입니다. 오른쪽 SQL을 순서대로 실행한다고 가정합니다.

CREATE TABLE test (id INTEGER PRIMARY KEY);

-- 세션 B
BEGIN;
INSERT INTO test VALUES (20);
-- 세션 A
BEGIN;
INSERT INTO test VALUES (21);
INSERT INTO test VALUES (20);
-- 다시 세션 B
INSERT INTO test VALUES (21);

각 화살표는 “내가 상대 트랜잭션 종료를 기다림”을 뜻합니다.

락 상태

상대 트랜잭션 번호에 이미 ExclusiveLock이 있어서 ShareLock 요청이 기다립니다.

여기서 잠기는 대상: 값 20이나 21의 행이 아니라 상대 트랜잭션입니다. `SELECT ... FOR SHARE/UPDATE`로 행을 잠그는 예제와는 다릅니다.

기억할 점

화살표는 한 트랜잭션이 다른 트랜잭션의 종료를 기다린다는 뜻입니다.

실행 순서

⑤와 ⑥에서 INSERT가 멈춥니다. ⑦에서 한쪽이 롤백된 뒤 B가 다시 진행합니다.

그림의 핵심 · 키 20과 21이 서로 락을 건 게 아닙니다. 중복 여부를 확인하려고 상대 트랜잭션이 끝나길 기다리다가 두 방향의 대기가 생깁니다.
정확성 근거와 범위
  • PostgreSQL 18 공식 문서 · Index Uniqueness Checks — 미커밋 삽입과 충돌 시 기다린 뒤 가시성을 다시 검사하는 이유.
  • PostgreSQL 18 공식 문서 · Explicit Locking — 테이블/행 락의 범위, deadlock 감지와 victim 선택은 예측할 수 없다는 설명.
  • PostgreSQL 18 공식 문서 · pg_locks — locktype, mode, granted 및 transaction ID 락을 보는 시스템 뷰.
  • PostgreSQL source · REL_18_STABLE · nbtinsert.c — B-tree 유니크 검사가 다른 트랜잭션을 기다리고 다시 검사하는 경로.
  • PostgreSQL source · REL_18_STABLE · lmgr.c — 실행 중인 XID에 `ExclusiveLock`을 놓고 상대 XID 대기에 `ShareLock`을 쓰는 경로.

확인 기준일: 2026-10-13. PostgreSQL 18 문서를 기준으로 한 학습 시뮬레이션이며 실제 서버 연결이나 특정 TRACEBACK 환경의 상태를 표시하지 않습니다. `pg_locks`에는 위 핵심 transactionid 행 외에도 테이블의 `RowExclusiveLock` 등 다른 락이 함께 보일 수 있습니다. deadlock detector는 어느 트랜잭션을 중단할지 보장하지 않으므로, 여기서는 A를 선택하는 예시를 사용합니다.
