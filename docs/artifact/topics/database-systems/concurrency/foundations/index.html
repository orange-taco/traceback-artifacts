INSERT만 했는데
왜 서로 멈출까?

두 트랜잭션이 서로 다른 값을 먼저 넣고, 이어서 상대가 넣은 값을 시도합니다. 중복 키 판단 → 트랜잭션 ID 락 → 대기 고리를 한 장면씩 읽어 보세요.

1왜 바로 중복 키 오류가 아닐까?상대의 INSERT가 아직 미커밋
2어디에 락을 요청할까?데이터 20·21이 아닌 상대 XID
3언제 데드락이 될까?대기 화살표가 고리를 만들 때

그림의 범위 · PostgreSQL의 test(id INTEGER PRIMARY KEY)를 가정합니다. XID 100·200은 이해를 위한 예시 번호입니다. TRACEBACK의 현재 DB 상태를 나타내는 그림은 아닙니다.

두 INSERT의 대기를 따라가기

먼저 전체 그림을 보고, 각 화살표가 생기는 이유를 단계별로 확인하세요.

전체 연결 / OVERVIEW

둘 다 자기 값을 넣고, 상대 값을 기다린다

트랜잭션 A · XID 100

INSERT 21

미커밋 · 자신의 XID 100에 ExclusiveLock 보유

트랜잭션 B · XID 200

INSERT 20

미커밋 · 자신의 XID 200에 ExclusiveLock 보유

A → B · A가 20을 시도하며 XID 200에 ShareLock 요청
B → A · B가 21을 시도하며 XID 100에 ShareLock 요청
A → B → A · 서로 끝나기를 기다리는 순환 대기
화살표는 대기 방향입니다. 데이터 20·21에 ShareLock을 건다는 뜻이 아닙니다.

먼저 읽을 것

각자 첫 INSERT는 끝났지만 COMMIT은 하지 않았습니다. 상대의 값을 다시 INSERT하면, 그 값이 최종적으로 남을지 알아야 합니다.

이 자료의 역할

여기서는 원인과 관계를 먼저 익힙니다. 실제 실행 순서, Lock Table, 감지·롤백·COMMIT은 다음 완성본에서 단계별로 봅니다.

1 / UNIQUE CHECK

미커밋 값은 아직 결과가 정해지지 않았다

B: INSERT 20 · 아직 COMMIT 전

A: INSERT 20을 시도. 기본 키가 겹쳐 보이지만 B의 트랜잭션이 끝나야 최종 판단을 할 수 있습니다.

B가 COMMIT하면A의 20은 중복 키가 되어 오류가 납니다.
B가 ROLLBACK하면B의 20이 사라져 A의 INSERT가 진행될 수 있습니다.
그래서 기다립니다. PostgreSQL은 B의 종료를 기다린 뒤 고유성 검사를 다시 합니다.

왜 INSERT만 했는데 대기할까?

PRIMARY KEY는 같은 값 두 개가 최종적으로 남지 않게 해야 합니다. 동시에 실행 중인 INSERT도 검사 대상입니다.

MVCC와의 관계

MVCC는 미커밋 행의 가시성을 다루지만, 유일성 판단에는 다른 트랜잭션의 최종 결과가 필요합니다.

2 / TRANSACTION ID LOCK

기다리는 대상은 상대의 트랜잭션 ID다

XID 200 · B의 트랜잭션B: ExclusiveLock 보유
A: ShareLock 요청 · WAITING
XID 100 · A의 트랜잭션A: ExclusiveLock 보유
B: ShareLock 요청 · WAITING
같은 XID에서 충돌합니다. 보유 중인 ExclusiveLock과 요청한 ShareLock은 동시에 허용되지 않습니다.

ExclusiveLock / ShareLock

트랜잭션은 자신의 XID에 ExclusiveLock을 보유합니다. 다른 트랜잭션의 종료를 기다릴 때 그 XID에 ShareLock을 요청합니다.

헷갈리기 쉬운 구분

이 그림은 transactionid 락입니다. SELECT FOR SHARE나 SELECT FOR UPDATE로 요청하는 행 수준 잠금과 구분해야 합니다.

3 / LOCK WAIT

한쪽만 기다리면 아직 데드락은 아니다

A · XID 100

WAITING

20을 넣기 위해 B의 XID 200이 끝나길 기다림

B · XID 200

RUNNING

20을 넣은 뒤 아직 COMMIT하지 않음

AShareLock 요청 →B의 XID 200
B가 끝날 수 있다면 A의 대기도 풀립니다. 이것이 일반적인 Lock Waiting입니다.

화살표 읽기

“A → B”는 A가 B의 종료를 기다린다는 뜻입니다. B가 COMMIT하거나 ROLLBACK하면 A가 고유성을 다시 검사합니다.

다음에 무슨 일이 생길까?

B가 끝나기 전에 A의 값 21을 INSERT하려고 하면, B도 A의 종료를 기다리게 됩니다.

4 / DEADLOCK

서로의 종료를 기다리면 고리가 닫힌다

A · XID 100

WAITING

XID 200에 ShareLock 요청

B · XID 200

WAITING

XID 100에 ShareLock 요청

A → B · A는 B의 종료를 기다림
B → A · B는 A의 종료를 기다림
DEADLOCK · A → B → A
PostgreSQL이 한쪽을 중단하면 그 트랜잭션의 락이 해제되어 다른 쪽이 다시 진행할 수 있습니다. 어느 쪽이 선택될지는 고정되어 있지 않습니다.

대기와 데드락의 차이

한 방향 대기는 상대가 종료하면 풀립니다. 두 방향 대기는 양쪽 모두 기다려 스스로 풀 수 없습니다.
