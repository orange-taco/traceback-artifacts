SEAT RESERVATION / CONCURRENCY

좌석 하나는 기다림.
두 좌석은 서로 기다릴 수 있다.

예약 A와 B가 동시에 움직일 때 대기·중복 예약·덮어쓰기·데드락을 각각 다른 문제로 읽어 봅니다. 아래 사례를 고르면 실행 순서와 좌석 상태가 함께 바뀝니다.

가정한 예시이미 존재하는 좌석 행 S1·S2를 예약합니다. 예시 SQL과 트랜잭션은 교육용 모델이며, TRACEBACK 서비스의 현재 예약 구현을 설명하지 않습니다. PostgreSQL과 MySQL InnoDB의 기본 개념을 구분해 적었습니다.

한 좌석 행만 잡는 두 예약

A: S1 보유←B: S1 대기

대기 화살표가 한쪽뿐이라 이 단순한 경우에는 교착 고리가 없습니다. 다만 상태 검사가 빠지면 덮어쓰기나 중복 예약은 여전히 생깁니다.

두 좌석을 반대로 잡는 두 예약

A: S1 보유⇄B: S2 보유

A는 S2를, B는 S1을 원하면 양쪽이 상대의 종료를 기다립니다. 이것이 순환 대기, 즉 데드락입니다.

실행 순서로 보기

단계를 누르거나 재생하면 현재까지 일어난 일만 진하게 표시됩니다.

재생은 선택 사항입니다. 그림의 화살표는 실제 물리적 데이터 이동이 아니라 트랜잭션의 대기 관계입니다.

그럼 무엇이 해결책일까?

하나의 기능으로 모든 문제를 막을 수는 없습니다. 좌석의 소유권을 하나로 확정하는 규칙과 여러 자원을 잡는 순서를 먼저 정하고, 실패했을 때 다시 시도하는 경로를 갖춥니다.

01 · 정합성

조건부 UPDATE 또는 유일한 예약 키

한 좌석 행에 상태를 저장한다면 available일 때만 UPDATE하고 영향받은 행이 1개인지 확인합니다. 별도 활성 예약 행을 INSERT한다면 UNIQUE(event_id, seat_id)가 이중 예약을 DB에서 거부합니다. 둘은 데이터 모델에 따른 선택지입니다. UNIQUE는 잘못된 경로까지 막는 최종 방어선이지만, 대기 순서까지 정해 주지는 않습니다.

02 · 여러 자원

모든 경로의 잠금·변경 순서를 통일

여러 좌석이면 ID 순서로 하나씩 잠그고, 예약 INSERT·쿠폰·주문 행 등 함께 만지는 자원도 전 경로에서 일관된 순서로 처리합니다. 그 사례의 순환 대기를 줄이는 핵심입니다. SQL의 ORDER BY만 붙이고 실제 잠금 획득 순서를 확인하지 않은 채 보장이라고 가정하면 안 됩니다.

03 · 실패 복구

짧은 트랜잭션 + 전체 재시도

DB가 데드락을 감지하면 한 트랜잭션을 중단합니다. 애플리케이션은 처음부터 상태를 다시 읽고 제한된 횟수·간격으로 재시도합니다. 이미 예약된 좌석이나 UNIQUE 충돌은 “재시도하면 반드시 성공”이 아니라 사용자에게 매진을 알려야 하는 결과일 수 있습니다.

04 · 운영 안전장치

타임아웃은 기다림의 상한

대기 시간을 제한해 요청이 끝없이 붙잡히지 않게 합니다. 데드락 예방책도, 중복 예약 방지책도 아닙니다. 타임아웃 이후 롤백 범위와 재시도 방식은 DB 설정에 따라 달라집니다.

권장 흐름: 좌석을 확정하는 한 트랜잭션

  1. 요청한 좌석 ID를 정렬하고, 필요한 행만 짧게 처리합니다.
  2. 각 좌석에 대해 status = 'available' 조건으로 변경하거나, 잠근 뒤 최신 상태를 다시 확인합니다.
  3. 모두 성공하면 같은 트랜잭션에서 예약을 기록하고 COMMIT합니다. 하나라도 실패하면 전체 ROLLBACK합니다.
  4. 데드락·일시적 동시성 오류는 전체 트랜잭션을 제한적으로 재시도하고, 이미 선점된 좌석은 실패로 안내합니다.

비관적 잠금 · 먼저 줄 서기

SELECT ... FOR UPDATE로 좌석 행을 잡고, 잠금을 얻은 뒤에 빈 좌석인지 검사합니다. 여러 좌석을 함께 확정하거나 충돌이 잦을 때 흐름을 이해하기 쉽습니다. 행 잠금 자체만으로는 잘못된 무조건 UPDATE나 역순 잠금의 교착을 고치지 못합니다.

낙관적 경쟁 · 조건으로 승자 정하기

UPDATE ... WHERE status = 'available' 또는 version = :seen_version으로 변경하고 영향받은 행 수를 확인합니다. 한 좌석에는 명시적 선잠금 없이도 원자적 선점이 가능합니다. 충돌이 잦으면 실패·재시도가 늘고, 여러 좌석의 전체 성공은 트랜잭션으로 묶어야 합니다.

-- 교육용 예시: 좌석 상태를 한 행에 보관하는 모델
BEGIN;
UPDATE seats
   SET status = 'reserved', reserved_by = :user_id
 WHERE event_id = :event_id AND seat_id = :seat_id
  AND status = 'available';
-- 앱에서 영향받은 행이 1개면 COMMIT
-- 0개면 이미 예약됨 → ROLLBACK

-- 별도 활성 예약 행 모델이라면 DB에 UNIQUE(event_id, seat_id) 필요
PostgreSQL과 InnoDB에서 어디가 다른가?

위 기존 좌석 행 UPDATE 사례는 두 엔진 모두 충돌하는 변경을 기다릴 수 있고, 반대 순서로 여러 행을 변경하면 교착이 가능합니다. 다만 잠금 구현과 오류 뒤 처리에는 차이가 있습니다.

  • PostgreSQL: 기본 READ COMMITTED에서 대기 후 UPDATE의 WHERE 조건을 새 행 버전에 다시 평가합니다. UNIQUE INSERT 충돌에서는 미완료 트랜잭션의 결과를 기다리며, 자세한 transactionid ShareLock 사례는 다음 페이지에 있습니다.
  • MySQL InnoDB: 잠금 읽기와 UPDATE는 인덱스 레코드 잠금에 관여합니다. 인덱스·검색 조건·격리 수준에 따라 잠금 범위가 커질 수 있습니다. UNIQUE INSERT의 대기 대상을 PostgreSQL의 XID ShareLock과 같은 것으로 설명하면 안 됩니다.
  • 오류 처리: InnoDB의 데드락은 전체 트랜잭션을 롤백하지만, 기본 lock wait timeout은 실패한 문장만 롤백합니다. 애플리케이션에서 트랜잭션을 명시적으로 정리하고 재시도 정책을 정해야 합니다.
놓치기 쉬운 경계
  • 한 좌석이어도 같은 트랜잭션에서 쿠폰·주문 등 다른 자원을 역순으로 잠그면 데드락이 가능합니다. “한 좌석은 절대 데드락이 없다”는 뜻이 아닙니다.
  • SELECT 후 INSERT는 읽은 시점의 빈자리만 말합니다. 예약 테이블에 유일성 제약이 없으면 두 예약 행이 모두 들어갈 수 있습니다.
  • 무조건 UPDATE는 앞선 예약자를 나중 예약자가 덮어쓸 수 있습니다. 행 잠금이 있더라도 최신 상태를 확인하지 않으면 업무 규칙은 지켜지지 않습니다.
  • 취소·재판매: 예약 이력을 같은 테이블에 남기면 모든 행에 단순 UNIQUE를 걸 수 없습니다. “활성 예약만 하나”라는 규칙에 맞는 스키마나 별도 현재 소유 행이 필요합니다.
  • MVCC는 일반 조회와 쓰기의 간섭을 줄여 주지만, 같은 좌석의 소유권 결정이나 여러 행의 잠금 순환을 없애지는 않습니다. SKIP LOCKED는 정확히 지정한 좌석을 건너뛸 수 있어 이 흐름의 기본 해결책이 아닙니다.
