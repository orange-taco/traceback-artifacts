INSERT만 했는데 왜 서로 멈출까?

두 트랜잭션이 상대가 끝나기를 기다리다 멈추는 과정을 한 장면씩 보세요.

그림의 범위 · PostgreSQL 18 / MySQL 8.4 InnoDB · test(id INTEGER PRIMARY KEY) · XID 100/200은 PostgreSQL 설명용 번호이며 TRACEBACK DB 상태가 아닙니다.

A와 B의 실행 흐름

보라색 화살표는 상대 XID가 끝나기를 기다리는 방향입니다.

① B · 20 먼저 저장BEGIN;
INSERT INTO test VALUES (20);
② A · 21 먼저 저장BEGIN;
INSERT INTO test VALUES (21);
③ A · 20 다시 시도INSERT INTO test VALUES (20);
④ B · 21 다시 시도INSERT INTO test VALUES (21);

공유 락은 왜 필요할까?

락의 이름은 함께 보유할 수 있는지를 말합니다. 무엇을 보호하거나 기다리는지는 잠금 대상에 따라 달라집니다.

공유 락 · Share (S)

여러 트랜잭션이 같은 대상을 함께 잠글 수 있습니다. 행을 보호할 때는 다른 트랜잭션의 변경을 막으면서 함께 읽을 수 있습니다.

배타 락 · Exclusive (X)

같은 대상의 S·X 요청과 함께 보유할 수 없습니다. PostgreSQL 예제에서는 자기 XID에, InnoDB 예제에서는 삽입한 기본 키의 인덱스 레코드에 X 락을 보유합니다.

같은 잠금 대상을 요청하면

별도 예시 · 대상은 상품의 행

가격을 바꾸지 못하게 보호

상품 가격이 10,000원일 때 A와 B가 같은 행을 FOR SHARE로 잠급니다.

A · FOR SHARE 🔒B · FOR SHARE 🔒C · UPDATE 대기 ⏳
SELECT price FROM products WHERE id = 1 FOR SHARE;

A와 B는 함께 보유하고 C의 해당 행 변경을 기다리게 합니다. A가 배타 성격의 FOR UPDATE를 썼다면 B도 기다려야 합니다. 단순 SELECT에는 이 행 잠금이 필요하지 않습니다.

PostgreSQL INSERT 예제 · 대상은 트랜잭션 ID

상대의 종료를 기다리기

B가 넣은 20의 중복 여부는 B의 COMMIT·ROLLBACK 결과에 달려 있습니다.

B · XID 200에 X 보유 🔒A · XID 200에 S 요청 ⏳
INSERT INTO test VALUES (20);

A의 S 요청은 B의 X와 충돌합니다. 20이라는 데이터에 공유 락을 건 것이 아닙니다. PostgreSQL은 이 충돌을 이용해 B가 끝날 때까지 기다립니다.

같은 INSERT 순서라도 잠금 대상이 다릅니다. PostgreSQL은 상대 XID에 ShareLock을 요청합니다. InnoDB는 중복된 기본 키의 인덱스 레코드에 공유 잠금을 요청합니다. FOR SHARE는 별도의 명시적 행 잠금 예시입니다. 두 DB 모두 일반적인 MVCC 조회는 쓰기를 막지 않습니다.
