왜 일반 SELECT도 테이블 잠금이 필요한가?

MVCC는 어떤 행 버전을 볼지 해결합니다. ACCESS SHARE는 쿼리가 관계를 사용하는 동안 DROP TABLE 같은 ACCESS EXCLUSIVE 작업과 충돌시켜 관계 자체를 보호합니다. 그래서 행 FOR SHARE 없이도 테이블 잠금은 필요합니다.

왜 SELECT FOR SHARE는 잠금을 두 층에서 쓰나?

테이블 ROW SHARE는 관계 수준 작업과 조정하고, 선택한 행의 FOR SHARE는 같은 행의 변경·삭제와 조정합니다. 같은 “SHARE” 표현이어도 대상과 역할이 다릅니다.

03 · PRACTICAL CASES

공통 원리를 좌석 예약에 적용

아래 여섯 시뮬레이션은 그대로 유지합니다. 대기·순환·일관된 잠금 순서는 공통 원리이고, 정확한 잠금 이름과 대기 관찰 방식은 위 엔진 탭에서 확인합니다.

① 한쪽만 기다림 · 일반적인 대기

A가 S1 보유←B가 S1 요청

B는 A가 끝나면 다시 진행합니다. 이 자체는 데드락이 아닙니다. 하지만 이후 상태를 검사하지 않으면 A의 예약을 덮어쓸 수 있습니다.

② 양쪽이 서로 기다림 · 데드락

A: S1 보유 · S2 대기⇄B: S2 보유 · S1 대기

둘 다 상대가 가진 좌석을 기다려 고리가 닫힙니다. DB는 한 트랜잭션을 중단해 고리를 끊습니다.

아래 사례는 예약을 저장하는 방식이 서로 다른 두 교육용 모델입니다. 같은 DB에서 순서대로 일어나는 여섯 단계가 아닙니다.

사례 01–05 · 기존 행 UPDATE

좌석 행이 현재 예약 상태를 저장

seats(event_id, seat_id, status, reserved_by)
S1 / available / 예약자 없음
→ UPDATE seats · S1 / reserved / 예약자 A

S2도 같은 방식입니다. 사례 05는 이미 있는 coupons(id, status)의 C1 행도 갱신하므로 잠금 순서가 중요합니다.

사례 06 · 새 행 INSERT

예약 내역을 별도 행으로 저장

seats(event_id, seat_id) · S1 행은 이미 존재
reservations(event_id, seat_id, user_id) · S1 예약 행 없음 → INSERT

이 모델은 새 예약 행을 만들고 UNIQUE로 중복을 막습니다. 필요하면 기존 S1 좌석 행을 먼저 잠글 수도 있습니다.

공통: 사례 01–05의 ‘보유’는 충돌하는 행/레코드 수준 보호를 뜻하고, 화살표는 대기 관계입니다. 엔진별: PostgreSQL의 행·XID 대기와 InnoDB의 인덱스 레코드·범위 잠금은 위 탭처럼 구현이 다릅니다. 사례 06은 예약 행 생성과 유일성 경쟁입니다.

실무에서는 세 가지 질문을 순서대로

행 락, UNIQUE, 정렬, 재시도는 같은 기능의 대안이 아닙니다. 서로 다른 실패를 막습니다.

1 · 정합성

한 좌석의 주인은 한 명인가?

좌석 상태 행이면 조건부 UPDATE와 변경 행 수를 확인합니다. 별도 활성 예약 행이면 UNIQUE를 DB에 둡니다. 이 규칙이 예약의 핵심입니다.

2 · 순서

여러 자원을 같은 순서로 잡는가?

좌석·쿠폰·예약 키처럼 충돌할 수 있는 자원에 접근하는 순서를 통일합니다. 여러 좌석은 정렬된 ID 순서로 하나씩 처리합니다.

3 · 복구

실패를 어떻게 끝내는가?

데드락은 전체 트랜잭션을 새로 재시도합니다. 이미 예약된 좌석은 매진으로 안내합니다. 타임아웃은 대기 시간의 상한입니다.

비관적 잠금: 먼저 잡고 확인

SELECT ... FOR UPDATE로 기존 좌석 행을 잠근 뒤 최신 상태를 검사합니다. 다중 좌석·복잡한 검증에 유용하지만, 잠금 순서와 상태 검사는 여전히 필요합니다.

낙관적 경쟁: 조건으로 승자 결정

UPDATE ... WHERE status='available' 또는 버전 조건을 사용하고 변경 행 수를 봅니다. 한 좌석에서는 간결합니다. 여러 좌석은 한 트랜잭션에서 전부 성공하거나 전부 취소해야 합니다.

한 좌석의 조건부 UPDATE · 교육용 SQL 예시
-- 좌석 상태를 한 행에 저장하는 모델
BEGIN;
UPDATE seats
   SET status = 'reserved', reserved_by = :user_id
 WHERE event_id = :event_id AND seat_id = :seat_id
  AND status = 'available';
-- 앱: 영향받은 행 1개 → COMMIT
-- 앱: 영향받은 행 0개 → ROLLBACK 및 매진 응답

이 모델은 좌석 행 자체가 현재 소유자를 표현합니다. 별도 활성 예약 행을 저장한다면 그 모델의 유일성 제약을 설계해야 합니다.

인덱스나 데이터 배치를 바꾸면 충돌도 사라질까?

먼저 찾는 방법과 좌석의 소유권을 구분하세요. 같은 S1을 두 요청이 확정하려는 한, 더 빨리 찾는 인덱스가 승자를 정해 주지는 않습니다.

파티셔닝 · 같은 DB 안에서 나눔

DB 하나→S1 파티션S2 파티션

행이 서로 다른 파티션에 있어도 두 좌석을 함께 잡는 트랜잭션은 역순으로 기다릴 수 있습니다.

샤딩 · 독립된 DB/샤드로 배치

샤드 A · S1│샤드 B · S2

독립적인 예약의 부하는 나뉩니다. 그러나 S1 요청 둘은 여전히 샤드 A에서 경쟁합니다.

일반 인덱스

같은 S1 충돌: 그대로

찾는 범위와 속도를 바꿉니다. id가 PK라면 이미 인덱스가 있습니다. InnoDB에서는 적절한 검색 인덱스가 넓은 스캔·잠금 범위를 줄일 수 있습니다.

PostgreSQL INCLUDE

같은 S1 충돌: 그대로

추가 열은 읽기용 payload이며 검색 키나 잠금 회피 수단이 아닙니다. UNIQUE (event_id, seat_id) INCLUDE (status)도 유일성은 앞의 두 키에만 적용됩니다. 자주 바뀌는 status를 담으면 인덱스 갱신 비용도 늘 수 있습니다.

파티셔닝

같은 S1 충돌: 그대로

한 좌석은 정해진 파티션으로 갑니다. PostgreSQL의 파티션 테이블에서 UNIQUE/PK는 파티션 키를 포함해야 하는 제약도 있습니다.

샤딩

배치는 달라짐 · 충돌은 조건부

서로 독립된 좌석은 DB 부하가 분산됩니다. 같은 좌석은 같은 샤드에서 경쟁하고, 여러 샤드를 한 번에 예약하면 분산 트랜잭션·원자성이 새 문제입니다.

핵심: 샤딩의 차이는 인덱스가 빨라져서가 아니라 데이터와 요청을 별도 DB/샤드로 배치하기 때문입니다. 샤딩도 이중 예약을 막는 조건부 변경·유일성 규칙을 대신하지 않습니다.

근거: PostgreSQL INCLUDE · PostgreSQL 파티셔닝 · InnoDB 검색·잠금 범위. 샤딩 설명은 분리된 DB에 좌석을 배치한 가정에서의 설계 추론입니다.

잠금에서 이어지는 세 가지 질문

아래는 좌석 예약 여섯 사례와 별개인 PostgreSQL 학습 예시입니다. 필요한 주제만 펼쳐 보세요.

1 · 2단계 잠금과 격리 수준은 무엇이 다를까?
잠금 획득·확장→잠금 해제

2단계 잠금(2PL)은 잠금을 얻는 단계와 해제하는 단계로 나눠 생각하는 동시성 제어 개념입니다. SELECT FOR UPDATE를 두 번 실행한다는 뜻은 아닙니다. PostgreSQL은 MVCC도 사용하므로 모든 일반 SELECT를 잠그는 2PL 모델로 단순화하면 안 됩니다.

READ COMMITTED: B의 UPDATE seats SET status='reserved' WHERE id=1 AND status='available'가 A의 변경을 기다렸다가, A가 커밋하면 바뀐 행 버전에서 WHERE를 다시 확인합니다. 이미 예약됐다면 변경 행은 0개입니다. REPEATABLE READ: B가 사용 중인 스냅샷 이후 A가 그 행을 바꾸고 커밋했다면 같은 UPDATE에서 직렬화 오류가 날 수 있어 전체 트랜잭션 재시도가 필요합니다. PostgreSQL 격리 수준 문서

2 · OFFSET과 커서 페이지네이션은 어떻게 다를까?
OFFSET · 앞의 N개를 계산해 건너뜀→커서 · 마지막 정렬 키 다음부터 찾음

큰 OFFSET은 건너뛸 행도 서버가 계산해야 합니다. 커서 방식은 마지막으로 받은 행의 (created_at, id)를 함께 저장하고 다음 페이지의 경계로 씁니다. id는 같은 생성 시각의 순서를 정합니다. 정렬에 맞는 인덱스가 있으면 다음 범위를 효율적으로 찾을 수 있습니다.

SELECT id, created_at FROM reservations WHERE (created_at, id) < (:last_created_at, :last_id) ORDER BY created_at DESC, id DESC LIMIT 20;

예시는 PostgreSQL의 내림차순 키셋 페이지네이션입니다. 다음 요청에 마지막 행의 두 값을 전달합니다. 커서는 읽기 위치를 뜻하며, 데이터가 중간에 수정되면 전체 목록의 고정 스냅샷을 보장하지는 않습니다. PostgreSQL LIMIT/OFFSET · 정렬과 비교

3 · 커넥션 풀과 PostgreSQL의 idle은 같은 뜻일까?
앱 요청→풀에서 DB 연결 빌림→반납·재사용

커넥션 풀은 스레드의 모음이 아니라 DB 연결을 재사용하는 장치입니다. PostgreSQL pg_stat_activity.state = 'idle'은 서버가 해당 연결에서 다음 명령을 기다린다는 뜻일 뿐, 앱 코드가 연결을 풀에 반납했는지는 알려 주지 않습니다. idle in transaction은 트랜잭션이 열린 채 명령을 기다리는 별도 상태입니다. PostgreSQL pg_stat_activity

TRACEBACK 코드 확인 범위: 백엔드 main의 Dockerfile · 354df65, 34–41행은 Gunicorn의 Uvicorn worker로 ASGI 앱을 실행하고, DB 설정 · 63–70행에는 conn_max_age=60이 있습니다. 제공된 실습 메모의 “ASGI 전환 후 연결 고갈·당시 WSGI 복귀”는 이 리비전에서 확인되지 않으며, 고갈 원인도 확인된 실험 결과로 제시하지 않습니다. ASGI만으로 원인을 단정하려면 실제 연결 수·요청 수·풀 설정·idle in transaction 등을 함께 관찰해야 합니다. Django 비동기 연결 안내

놓치기 쉬운 경계
  • 한 좌석이어도 같은 트랜잭션에서 쿠폰·주문 등 다른 자원을 역순으로 잠그면 데드락이 가능합니다. “한 좌석은 절대 데드락이 없다”는 뜻이 아닙니다.
  • SELECT 후 INSERT는 읽은 시점의 빈자리만 말합니다. 예약 테이블에 유일성 제약이 없으면 두 예약 행이 모두 들어갈 수 있습니다.
  • 무조건 UPDATE는 앞선 예약자를 나중 예약자가 덮어쓸 수 있습니다. 행 잠금이 있더라도 최신 상태를 확인하지 않으면 업무 규칙은 지켜지지 않습니다.
  • 취소·재판매: 예약 이력을 같은 테이블에 남기면 모든 행에 단순 UNIQUE를 걸 수 없습니다. “활성 예약만 하나”라는 규칙에 맞는 스키마나 별도 현재 소유 행이 필요합니다.
  • MVCC는 일반 조회와 쓰기의 간섭을 줄여 주지만, 같은 좌석의 소유권 결정이나 여러 행의 잠금 순환을 없애지는 않습니다. SKIP LOCKED는 정확히 지정한 좌석을 건너뛸 수 있어 이 흐름의 기본 해결책이 아닙니다.
실서비스에서는 요청 재시도와 결제도 분리해서 생각
  • 중복 요청: 사용자의 재클릭이나 네트워크 재시도로 같은 예약 요청이 다시 올 수 있습니다. 요청별 멱등 키를 두면 같은 요청을 한 번의 결과로 묶을 수 있습니다. 좌석의 DB 유일성 규칙도 별도로 유지해야 합니다.
  • 결제 대기: 결제 서비스의 응답을 기다리는 동안 좌석 행 잠금을 오래 보유하지 않도록 예약 보류 기간·만료·확정 흐름을 설계합니다. 만료 처리와 재판매가 가능한 스키마인지 함께 확인합니다.
  • 타임아웃: 요청을 빨리 실패시키는 운영 장치입니다. 실패한 문장과 트랜잭션의 처리 범위는 DB마다 다르므로, 앱에서 명시적으로 정리한 뒤 재시도 여부를 판단합니다.
