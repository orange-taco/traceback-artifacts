서비스 전체 구성

TRACEBACK은 온라인 스토어를 만들고 있습니다. 화면은 Client 저장소에서 Vercel로, API는 Server 저장소에서 AWS로 배포하도록 구성했습니다. 아래에는 고객 요청이 지나는 길과 두 배포의 실제 설정을 함께 그렸습니다.

이 페이지의 콘솔·접속 관찰은 2026-09-26~10-08 기록입니다. 코드는 아래에 적힌 revision에서 확인했습니다. 지금 외부에서 끝까지 동작하는 서비스라고 판단하지 않습니다.

고객 요청은 어디로 가나요?

위에서부터 고객이 화면을 열고 API를 부르는 경로입니다. DNS는 주소를 답하고, HTTP 요청은 그 주소로 별도 연결됩니다.

인증/API 요청 /_allauth/*, /accounts/*, /api/*

브라우저 → Vercel rewrite → 개발 API 주소 → EC2. 2026-10-04 rewrite 적용은 관찰됐지만 API HTTPS 연결 실패로 502였습니다.

첫 실패 지점: 당시 DNS A 레코드와 EC2의 HTTP 80·ACME 경로는 확인됐습니다. HTTPS 443의 인증서·Nginx 프록시, Django 실행, RDS 연결이 이어서 필요했습니다. 프런트가 200을 반환해도 API가 동작한다는 뜻은 아닙니다.

이 구성을 만드는 두 배포 경로

고객 요청 경로와 배포 경로는 다릅니다. Client와 Server는 저장소·설정 장소·배포 대상이 각각 있습니다.

  1. traceback-client · developmentReact Router SSR 코드와 vercel.ts
  2. Vercel 개발 프로젝트Production Branch = development; 프로젝트의 Production 범위는 개발 서비스용

  4. 개발 프런트 URLtraceback-client-nine.vercel.app; 화면 200, API 502 관찰

왜 공개 EC2와 private RDS인가? 다른 구성과 비교

현재 선택: 개발 비용과 구성 요소를 줄이기 위해 공개 서브넷의 EC2 한 대에 Nginx를 두고 DB는 인터넷에서 직접 닿지 않는 RDS에 둡니다. NAT Gateway와 Load Balancer는 사용하지 않는 설계입니다.

대안: ALB를 공개 입구로 두고 앱 EC2를 비공개 서브넷에 놓을 수 있습니다. 앱 호스트 노출을 줄이고 확장하기 쉽지만 별도 리소스·비용·설정이 필요합니다. 운영 환경까지 이 개발 구조로 확정했다는 뜻은 아닙니다.

왜 GitHub 배포 role과 EC2 instance role을 따로 두나?

GitHub runner는 ECR에 이미지를 올리고 SSM 명령을 보냅니다. EC2는 자신의 role로 ECR에서 이미지를 내려받고 SSM Agent로 통신합니다. 주체와 권한이 다르므로 role을 분리했습니다. 사람이 EC2 셸을 여는 권한은 또 별도입니다.

대안인 장기 AWS access key를 GitHub에 저장하면 키 발급·보관·회전이 필요합니다. 현재 구성은 OIDC 일시 자격을 선택했습니다.

왜 RDS를 쓰고 EC2 안의 로컬 DB를 제거하나?

로컬 개발에서는 Docker Compose가 PostgreSQL 컨테이너를 함께 띄웁니다. AWS 개발 EC2에서는 서버용 Compose override가 그 db 서비스를 제거하고 private RDS에 연결하도록 정의됐습니다. DB를 앱 컨테이너와 분리해 서버 재배포와 DB 보관 경계를 나누지만, RDS 계정·네트워크·백업도 따로 설정해야 합니다.

대안은 EC2 한 대에 앱과 PostgreSQL을 함께 두는 것입니다. 자원이 적지만 그 서버의 디스크·DB 백업·복구까지 직접 책임져야 합니다.

AWS와 배포 서비스 이름

VPC 안의 서브넷⊃EC2 네트워크 인터페이스↔Security Group
VPC · subnet · route table · Internet Gateway
VPC는 AWS의 가상 네트워크입니다. 서브넷은 그 안의 주소 구획이며 EC2는 서브넷에 놓입니다. 서브넷의 route table은 목적지 경로를 정하고 Internet Gateway는 인터넷 경로의 출입구입니다. Security Group은 별도로 연결 허용 여부를 정합니다.
EC2 · EIP · Security Group
EC2는 AWS의 가상 컴퓨터입니다. EIP는 그 컴퓨터에 연결한 고정 공인 IPv4이고, Security Group은 들어오고 나가는 연결의 허용 규칙입니다. 서로 대체 관계가 아닙니다.
Route 53 · RDS · ECR · SSM
Route 53은 DNS 응답, RDS는 관리형 PostgreSQL, ECR은 컨테이너 이미지 보관, SSM은 EC2 원격 명령에 쓰입니다. 각각 다른 단계의 자원입니다.
Vercel · GitHub Environment
Vercel은 Client SSR을 배포합니다. GitHub Environment는 Actions가 읽는 AWS 배포 변수와 규칙을 저장합니다. EC2의 Django 비밀값 저장소는 아닙니다.

일반 네트워크·코드 개념

DNS로 IP 조회→IP:443에 연결→TLS · HTTP 요청
SSR · API · rewrite
SSR은 서버에서 HTML을 만들어 보내는 방식입니다. API는 데이터·동작 요청의 입구이고, rewrite는 프런트 주소로 받은 특정 경로를 다른 서버로 전달하는 규칙입니다.
DNS · IP · TLS · reverse proxy
DNS는 이름에 대한 IP를 알려줍니다. 그다음 요청자는 IP의 443 포트에 연결해 TLS로 암호화하고 HTTP를 보냅니다. Nginx reverse proxy는 받은 요청을 Django로 전달합니다.
인바운드 · 아웃바운드 · NACL
인바운드는 자원으로 들어오는 새 연결, 아웃바운드는 밖으로 나가는 연결입니다. NACL은 서브넷의 별도 접근 규칙이며 Security Group과 둘 다 통과해야 합니다. 현재 NACL 세부 규칙은 확인되지 않았습니다.
환경변수 · 이미지 digest · migration
환경변수는 실행 환경이 프로그램에 주는 값입니다. 이미지 digest는 배포할 컨테이너 내용을 고정한 식별자이고, migration은 DB 구조를 코드와 맞추는 단계입니다.

코드 확인: backend PR #12 phase-0-development-deployment 9e2108948c72, client development afd7664ce2e1. 콘솔·접속 값에는 관찰 날짜를 붙였습니다. 현재 상태는 해당 서비스에서 다시 확인해야 합니다.
