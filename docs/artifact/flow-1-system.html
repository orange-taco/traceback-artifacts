서비스 전체 구성

TRACEBACK은 온라인 스토어를 만들고 있습니다. 화면은 Client 저장소에서 Vercel로, API는 Server 저장소에서 AWS로 배포하도록 구성했습니다. 아래에는 고객 요청이 지나는 길과 두 배포의 실제 설정을 함께 그렸습니다.

이 페이지의 콘솔·접속 관찰은 2026-09-26~10-08 기록입니다. 코드는 아래에 적힌 revision에서 확인했습니다. 지금 외부에서 끝까지 동작하는 서비스라고 판단하지 않습니다.

고객 요청은 어디로 가나요?

위에서부터 고객이 화면을 열고 API를 부르는 경로입니다. DNS는 주소를 답하고, HTTP 요청은 그 주소로 별도 연결됩니다.

화면 요청 /, /auth/login

브라우저 → Vercel SSR → 브라우저. 2026-09-26 두 경로의 HTTP 200이 기록됐습니다. 현재 제품 화면의 상당 부분은 와이어프레임입니다.

인증/API 요청 /_allauth/*, /accounts/*, /api/*

브라우저 → Vercel rewrite → 개발 API 주소 → EC2. 2026-10-04 rewrite 적용은 관찰됐지만 API HTTPS 연결 실패로 502였습니다.

첫 실패 지점: 당시 DNS A 레코드와 EC2의 HTTP 80·ACME 경로는 확인됐습니다. HTTPS 443의 인증서·Nginx 프록시, Django 실행, RDS 연결이 이어서 필요했습니다. 프런트가 200을 반환해도 API가 동작한다는 뜻은 아닙니다.

이 구성을 만드는 두 배포 경로

고객 요청 경로와 배포 경로는 다릅니다. Client와 Server는 저장소·설정 장소·배포 대상이 각각 있습니다.

Client 저장소 → Vercel

  1. traceback-client · developmentReact Router SSR 코드와 vercel.ts
  2. Vercel 개발 프로젝트Production Branch = development; 프로젝트의 Production 범위는 개발 서비스용
  3. DJANGO_ORIGIN 설정 후 재배포https://api.dev-traceback.com을 Vercel 빌드가 읽고 세 API 경로 rewrite 생성
  4. 개발 프런트 URLtraceback-client-nine.vercel.app; 화면 200, API 502 관찰

Server 저장소 → AWS

  1. traceback · development pushquality/test 통과 시 배포 workflow를 호출하도록 PR #12 코드에 정의
  2. GitHub Environment → AWSdevelopment 변수; OIDC로 IAM role 사용
  3. ECR → SSM → 개발 EC2이미지를 digest로 지정해 원격 명령; EC2의 별도 .env가 앱에 전달됨
  4. EC2 → private RDS개발 DB와 5432 규칙은 당시 관찰; 앱 연결은 미검증

코드와 실행 상태 구분: Server 배포 workflow는 백엔드 PR #12의 phase-0-development-deployment revision에서 확인했습니다. 이 코드가 배포 완료를 뜻하지 않습니다. 운영용 Vercel·EC2·RDS는 별도 환경으로 계획되어 있으나 당시 준비·검증되지 않았습니다.

왜 Client SSR을 Vercel에 두고 Django EC2와 분리했나?

TRACEBACK 선택: React Router SSR은 Vercel 개발 프로젝트에, Django API는 AWS EC2에 둡니다. 프런트 배포와 서버 배포가 독립적이며 각자의 환경변수와 장애 지점을 따로 확인할 수 있습니다.

대안: 한 EC2에 SSR과 Django를 함께 두면 배포 대상은 하나이지만 Node SSR 런타임·Django·Nginx·TLS를 그 서버에서 함께 운영해야 합니다. 현재 확인한 Client 배포 기록은 Vercel SSR의 두 화면 경로가 200을 반환했다는 범위까지입니다.

근거: Client 개발 배포 기록 22–34행 · 화면 경로 코드 8–32행

Vercel에서 개발 API 주소와 rewrite 지정환경변수 위치·실제 값·코드 적용 · 2026-10-04 관찰
  1. 개발 Vercel 프로젝트의 Environment Variables → Production 범위에 DJANGO_ORIGIN=https://api.dev-traceback.com을 저장했습니다. 이 Production은 개발 프로젝트 안의 배포 범위입니다.
  2. 재배포하면 vercel.ts가 이 값을 읽어 HTTPS origin인지 검사하고, /_allauth/*, /accounts/*, /api/*를 해당 서버로 보냅니다.
  3. 당시 rewrite 적용은 확인했지만 API 응답은 502였습니다. 목적지 EC2의 HTTPS 443이 준비되지 않았기 때문입니다.
브라우저의 프런트 URL /api/*→Vercel rewrite→https://api.dev-traceback.com/api/*
왜 브라우저가 API 도메인을 직접 호출하지 않나?

TRACEBACK 선택: 프런트 도메인의 /_allauth/*, /accounts/*, /api/*를 Vercel에서 Django origin으로 전달합니다. 브라우저가 보는 요청 주소는 프런트 도메인에 남습니다.

대안: 브라우저 코드에서 API 도메인을 직접 호출할 수 있지만 프런트와 API가 서로 다른 origin이 되어 CORS, 쿠키와 CSRF 범위를 함께 설계·검증해야 합니다. 현재 코드는 Vercel rewrite 경로를 정의하며, 세션·로그인 성공은 별도 검증 대상입니다.

코드 설명: process.env.DJANGO_ORIGIN을 Vercel 배포가 읽습니다. 값이 없으면 rewrite 목록은 비어 있고, HTTPS origin 형식이 아니면 빌드 설정이 오류를 냅니다.

왜 공개 EC2와 private RDS인가? 다른 구성과 비교

현재 선택: 개발 비용과 구성 요소를 줄이기 위해 공개 서브넷의 EC2 한 대에 Nginx를 두고 DB는 인터넷에서 직접 닿지 않는 RDS에 둡니다. NAT Gateway와 Load Balancer는 사용하지 않는 설계입니다.

대안: ALB를 공개 입구로 두고 앱 EC2를 비공개 서브넷에 놓을 수 있습니다. 앱 호스트 노출을 줄이고 확장하기 쉽지만 별도 리소스·비용·설정이 필요합니다. 운영 환경까지 이 개발 구조로 확정했다는 뜻은 아닙니다.

왜 GitHub 배포 role과 EC2 instance role을 따로 두나?

GitHub runner는 ECR에 이미지를 올리고 SSM 명령을 보냅니다. EC2는 자신의 role로 ECR에서 이미지를 내려받고 SSM Agent로 통신합니다. 주체와 권한이 다르므로 role을 분리했습니다. 사람이 EC2 셸을 여는 권한은 또 별도입니다.

대안인 장기 AWS access key를 GitHub에 저장하면 키 발급·보관·회전이 필요합니다. 현재 구성은 OIDC 일시 자격을 선택했습니다.

왜 RDS를 쓰고 EC2 안의 로컬 DB를 제거하나?

로컬 개발에서는 Docker Compose가 PostgreSQL 컨테이너를 함께 띄웁니다. AWS 개발 EC2에서는 서버용 Compose override가 그 db 서비스를 제거하고 private RDS에 연결하도록 정의됐습니다. DB를 앱 컨테이너와 분리해 서버 재배포와 DB 보관 경계를 나누지만, RDS 계정·네트워크·백업도 따로 설정해야 합니다.

대안은 EC2 한 대에 앱과 PostgreSQL을 함께 두는 것입니다. 자원이 적지만 그 서버의 디스크·DB 백업·복구까지 직접 책임져야 합니다.

HTTPS를 EC2의 Nginx에서 끝내는 선택과 대안

TRACEBACK 개발 경로: 별도 로드 밸런서 없이 EC2의 Nginx가 인증서와 443 요청을 처리하고 로컬 Django로 넘기도록 준비 중입니다. HTTP 80의 ACME 확인 경로는 관찰됐지만 인증서·443 수신·프록시는 당시 끝나지 않았습니다.

대안: ALB에서 TLS를 종료하고 뒤의 EC2로 전달할 수 있습니다. 인증서 관리와 여러 서버 분산이 쉬워지지만 로드 밸런서 비용과 대상 그룹·보안 그룹 설정이 추가됩니다. 현재 개발 환경에는 ALB가 없습니다.

화면은 Vercel에서 끝나고, API만 새 연결을 만듭니다

브라우저에서 같은 프런트 주소를 열어도 요청 경로에 따라 결과가 갈립니다. SSR은 Vercel이 HTML을 만들어 돌려주는 일이고, rewrite는 Vercel이 받은 일부 경로를 Django origin으로 전달하는 설정입니다.

화면: GET /auth/login
브라우저요청 →Vercel SSRHTML →브라우저

2026-09-26의 HTTP 200은 이 길을 확인한 기록입니다. 이 화면의 성공으로 Django나 DB의 상태를 알 수는 없습니다.

API: GET /_allauth/browser/v1/config
브라우저요청 →Vercel rewrite새 요청 →API origin

브라우저의 요청 주소는 프런트 도메인입니다. vercel.ts는 DJANGO_ORIGIN을 목적지로 사용합니다. 당시 API HTTPS가 연결되지 않아 502였습니다.

  1. 1 · 이름 찾기DNSVercel 쪽에서 api.dev-traceback.com의 IPv4를 찾습니다. Route 53의 A 레코드는 3.34.78.140을 답합니다.
  2. 2 · 새 연결IP와 TCP 443주소를 안 뒤 Vercel이 그 IP의 443 포트에 연결합니다. DNS 서버가 HTTP 요청을 대신 전달하지는 않습니다.
  3. 3 · 암호화 · 당시 중단TLS와 NginxEC2의 Nginx가 인증서를 제시하고 HTTPS를 받아야 합니다. 당시 보안 그룹의 443 허용만 있었고 수신 서비스는 미완료였습니다.
  4. 4 · 앱 응답 · 미검증Django와 RDSNginx가 Django로 넘기고 앱이 필요하면 private RDS를 조회합니다. 이 왕복은 당시 확인되지 않았습니다.

HTTP와 HTTPS는 무엇이 다른가? HTTP는 요청·응답의 형식이고, HTTPS는 그 HTTP 통신에 TLS 암호화와 서버 인증을 더합니다. 포트 443을 보안 그룹에서 허용해도 Nginx의 인증서와 수신 설정이 없으면 HTTPS가 완성되지 않습니다.

reverse proxy는 누구인가? 이 구성에서는 EC2의 Nginx입니다. 공개 연결을 먼저 받고, 같은 EC2 안의 Django 앱으로 요청을 넘기는 역할입니다.

AWS 서비스·자원 · ② 네트워크의 소속과 독립된 규칙

EC2는 서브넷 안에 있고, 길과 허용 규칙은 따로 정합니다

아래 테두리는 포함 관계입니다. VPC 안에 서브넷이 있고, EC2의 네트워크 인터페이스가 서브넷의 주소를 사용합니다. RDS는 인터넷에서 직접 접속시키지 않는 별도 DB 경계입니다.

VPC · vpc-052ff4cb02c74522e · AWS 가상 네트워크
공개 기본 서브넷 · subnet-0ddcdfb74ab0d7121EC2 i-051f85a1ac4e64a2c

서브넷의 main route table에는 0.0.0.0/0 → Internet Gateway가 있었습니다. EC2에 EIP 3.34.78.140이 연결됐고, EC2 보안 그룹은 인터넷에서 80/443을 허용했습니다.

private DB 경계 · 인터넷 직접 접속 비활성 관찰RDS PostgreSQL

DB 보안 그룹은 TCP 5432의 출처로 개발 EC2 보안 그룹을 지정했습니다. 앱 계정·실제 연결은 확인 전입니다.

화살표의 뜻: 인터넷의 Vercel → EC2 EIP:443은 고객 API 요청입니다. EC2 → RDS:5432는 Django가 DB에 연결할 때의 별도 요청입니다. 위의 VPC·서브넷 테두리는 트래픽 화살표가 아닙니다.

Route table · 어디로?서브넷이 목적지에 따라 다음 경로를 고릅니다. 이 개발 서브넷은 명시적 연결 없이 main table을 사용했습니다.
Security Group · 허용하나?EC2 또는 RDS의 연결 허용 규칙입니다. EC2 443과 RDS 5432는 각각 다른 대상과 출처를 검사합니다.
IAM role · 누가 AWS API를?GitHub runner와 EC2가 AWS API를 호출할 권한입니다. 웹 요청의 443이나 DB의 5432를 여는 규칙이 아닙니다.
EIP가 있는데 왜 DNS도 필요한가?

EIP는 EC2에 붙인 숫자 주소입니다. Route 53의 A 레코드는 api.dev-traceback.com이라는 이름을 그 주소에 연결합니다. DNS가 성공해도 EC2의 웹 서비스가 자동 실행되지는 않습니다.

NACL은 어디서 확인하나?

NACL은 서브넷 수준의 추가 통신 규칙입니다. EC2·RDS 보안 그룹과 별개입니다. 이 프로젝트의 상세 NACL 값은 당시 기록에서 확인되지 않아 통과 상태를 단정하지 않습니다.

AWS의 일반 동작 근거: 서브넷과 route table · Security Group과 NACL. TRACEBACK 값은 위 03단계의 날짜 붙은 관찰 기록입니다.

AWS·GitHub와 일반 배포 개념 · ③ 코드를 서버로 보내기

이미지를 올리는 주체와 내려받는 주체가 다릅니다

아래 경로는 백엔드 PR #12의 배포 코드입니다. 실제 AWS 배포 완료 기록으로 읽으면 안 됩니다. CI는 변경 검사, CD는 그 결과물을 대상 환경에 배포하는 단계입니다.

  1. 1 · 검사GitHub Actionsdevelopment push에서 quality/test가 성공해야 개발 배포 job이 호출됩니다.
  2. 2 · 게시 권한OIDC → deploy roleGitHub runner가 일시적인 AWS 권한으로 ECR에 이미지를 올립니다. 장기 access key를 GitHub에 두지 않습니다.
  3. 3 · 원격 배포ECR digest → SSM내용으로 고정한 이미지 digest를 지정하고 SSM Run Command로 개발 EC2에 명령을 보냅니다.
  4. 4 · 서버 실행 · 미검증EC2 role → ComposeEC2는 자기 role로 ECR 이미지를 pull합니다. Compose가 EC2의 .env를 읽어 앱을 실행하고 RDS에 연결해야 합니다.
OIDC와 IAM role은 무엇이 다른가?

OIDC는 GitHub 작업이 자신의 신원을 AWS에 증명하는 방식입니다. IAM role은 AWS가 그 신원에 맡길 수 있는 권한 묶음입니다. 개발 배포 role과 EC2 instance role은 서로 다른 주체에 붙습니다.

digest, SSM, migration은 왜 필요한가?

digest는 실행할 이미지 내용을 고정합니다. SSM Run Command는 그 이미지를 EC2에서 실행하라는 명령을 보냅니다. migration은 새 앱 코드가 기대하는 DB 구조를 맞추는 작업이며, 앱 시작 전에 수행하도록 코드에 정의됐습니다.

일반 서비스 설명: GitHub OIDC용 AWS role · SSM Run Command. TRACEBACK의 실제 배포 분기와 명령은 위 04·05단계의 고정 revision 링크에서 확인합니다.
